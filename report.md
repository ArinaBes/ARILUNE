## Задание 1. Ветка для фичи
**Вопрос:** Почему в `main` теперь нет коммита про корзину? Откройте `index.html` в `main` — есть ли там блок корзины? Объясните своими словами, что такое «отдельная линия истории».

 В `main` нет коммита про корзину, потому что мы делали его в ветке `feature/cart`. В `main` файл `index.html` остался в старом состоянии — без блока корзины. Ветка — это отдельная линия истории, которая ответвляется от `main` и развивается параллельно. Пока мы не сделаем слияние (merge), изменения из одной ветки не попадают в другую.

 ## Задание 2. Смёржить фичу через Pull Request
**Вопрос:** Что показывает GitHub в diff PR? Зачем нужен Pull Request, если можно смёржить напрямую?

GitHub в diff PR показывает разницу между ветками: зелёным — добавленные строки, красным — удалённые. Pull Request нужен для того, чтобы: 1) код проверили другие разработчики перед слиянием; 2) можно было обсудить изменения в комментариях; 3) история оставалась чистой и понятной. Прямой merge в VS Code тоже работает, но PR — это стандарт командной разработки, потому что включает этап проверки.

## Задание 3. Смоделировать конфликт
**Вопрос:** Вставьте в отчёт содержимое файла в момент конфликта (как оно выглядит с маркерами) и то, что получилось после. Почему Git не «решил сам»?

Содержимое файла `price.txt` в момент конфликта:
<<<<<<< HEAD
Цена = 90
=======
Цена = 110
origin/main

Я оставила вариант **`90`** (свою версию). После разрешения файл выглядит так:
Цена = 90

Git не решил сам, потому что обе стороны осмысленно изменили одну и ту же строку по-разному. Только человек знает, какая цена верна (или как объединить оба варианта). Git отказывается угадывать и просит выбрать — это и есть разрешение конфликта.

## Задание 4. Pull request — второй раунд
**Вопрос:** Чем этот PR отличается от предыдущего? Что полезного в том, что GitHub показывает diff перед тем, как разрешить слить?

Этот PR отличается тем, что изменения в нём не конфликтуют с `main` (мы добавили новую строку с полем поиска, а не меняли существующую). GitHub показывает diff перед слиянием, чтобы разработчик мог убедиться, что изменения корректны: что не удалено лишнее, что нет опечаток, что добавлено именно то, что нужно. Это защищает от случайных ошибок и позволяет проверить код перед тем, как он попадёт в основную ветку.

## Задание 5. Синхронизация с GitHub в команде
**Вопрос:** Что произошло при ⇄ Sync (Pull)? Почему команда «Sync (Pull) перед Sync (Push)» снижает шанс конфликта?

При ⇄ Sync Git сначала скачал чужие изменения с GitHub (Pull) — то есть строку, которую добавил «напарник» в README.md. Затем Git попытался объединить их с моими локальными изменениями. Но так как мы оба изменили одну и ту же область файла, возник **конфликт** — Git не смог решить его автоматически.

Я разрешила конфликт вручную: удалила маркеры `<<<<<<<`, `=======`, `>>>>>>>` и оставила . Затем закоммитила разрешение: 
# Магазин свечей ARILUNA
Учебный проект по веб-программированию.
Автор: Бессарабова Арина МКНб-231

Команда «Sync (Pull) перед Sync (Push)» снижает шанс конфликта, потому что вы работаете поверх актуального состояния проекта, а не поверх устаревшего. Если сначала Pull — вы видите чужие правки и можете с ними считаться. Если сразу Push — Git отклонит отправку, потому что на сервере есть чужие коммиты, которых нет у вас локально.

## Задание 6. Безопасный откат в общей истории
**Вопрос:** Почему выбран `revert`, а не `reset` + `push --force`? Что случилось бы с историей вашей команды, если бы вы использовали force-push?

`revert` выбран потому, что он **безопасен для общей истории**: создаёт новый коммит, который отменяет изменения, не трогая уже существующие коммиты. Все члены команды видят, что был ошибочный коммит и что его отменили.

`reset` + `push --force` **перезаписывает историю**, удаляя коммиты. Если бы я использовал force-push, у моих коллег при следующем `pull` возникли бы ошибки: их локальная история разошлась бы с серверной, и им пришлось бы вручную исправлять конфликты. Force-push запрещён в большинстве команд именно поэтому.

## Задание 7. Удалить влитую ветку
**Вопрос:** Почему нельзя удалить ветку, на которой вы сейчас работаете? Что произойдёт, если попробовать удалить `main`?

 Нельзя удалить ветку, потому что Git не знаем, куда «переключить» ваше рабочее дерево —  останемся без точки опоры. Если попробовать удалить `main`, Git выдаст ошибку: «Cannot delete branch 'main' checked out at...». Даже если переключиться на другую ветку и попробовать удалить `main`, Git откажется, потому что `main` — это основная ветка, и в большинстве настроек она защищена от удаления. Кроме того, удаление `main` сломало бы всю структуру репозитория.
