## Задание 1. Ветка для фичи
**Вопрос:** Почему в `main` теперь нет коммита про корзину? Откройте `index.html` в `main` — есть ли там блок корзины? Объясните своими словами, что такое «отдельная линия истории».

 В `main` нет коммита про корзину, потому что мы делали его в ветке `feature/cart`. В `main` файл `index.html` остался в старом состоянии — без блока корзины. Ветка — это отдельная линия истории, которая ответвляется от `main` и развивается параллельно. Пока мы не сделаем слияние (merge), изменения из одной ветки не попадают в другую.

 ## Задание 2. Смёржить фичу через Pull Request
**Вопрос:** Что показывает GitHub в diff PR? Зачем нужен Pull Request, если можно смёржить напрямую?

GitHub в diff PR показывает разницу между ветками: зелёным — добавленные строки, красным — удалённые. Pull Request нужен для того, чтобы: 1) код проверили другие разработчики перед слиянием; 2) можно было обсудить изменения в комментариях; 3) история оставалась чистой и понятной. Прямой merge в VS Code тоже работает, но PR — это стандарт командной разработки, потому что включает этап проверки.

## Задание 3. Смоделировать конфликт
**Вопрос:** Вставьте в отчёт содержимое файла в момент конфликта (как оно выглядит с маркерами) и то, что получилось после. Почему Git не «решил сам»?

Содержимое файла `price.txt` в момент конфликта:
<<<<<<< HEAD
Цена = 90
=======
Цена = 110
origin/main

Я оставила вариант **`90`** (свою версию). После разрешения файл выглядит так:
Цена = 90

Git не решил сам, потому что обе стороны осмысленно изменили одну и ту же строку по-разному. Только человек знает, какая цена верна (или как объединить оба варианта). Git отказывается угадывать и просит выбрать — это и есть разрешение конфликта.

## Задание 4. Pull request — второй раунд
**Вопрос:** Чем этот PR отличается от предыдущего? Что полезного в том, что GitHub показывает diff перед тем, как разрешить слить?

Этот PR отличается тем, что изменения в нём не конфликтуют с `main` (мы добавили новую строку с полем поиска, а не меняли существующую). GitHub показывает diff перед слиянием, чтобы разработчик мог убедиться, что изменения корректны: что не удалено лишнее, что нет опечаток, что добавлено именно то, что нужно. Это защищает от случайных ошибок и позволяет проверить код перед тем, как он попадёт в основную ветку.
